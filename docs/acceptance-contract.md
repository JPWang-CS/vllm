# 实验阶段与验收

一次实验先固定配置和输入，再依次检查环境、运行模型、评测并清理资源。`fullnet plan` 保存本次所需阶段；`fullnet run` 执行它们，`fullnet status` 和报告展示各阶段结果。

## 固定执行顺序

| 阶段 | 检查内容 |
|---|---|
| 资产与依赖 | 权重、tokenizer、固定输入、实际运行环境和插件依赖 |
| 设备 | 当前物理卡与运行时编号的映射、健康和空闲状态 |
| 模型类 | 用实际模型 Python 加载插件，解析最终注册类，记录类名与源码位置 |
| 启动与短生成 | 服务就绪后发送真实生成请求，保存请求和响应 |
| KV 交接 | P/D 部署用同一请求核对两端传输证据，再进入固定评测 |
| 固定评测 | 保留样本 ID、模板、预算、评分函数、失败和截断统计 |
| 性能与 profile | 按冻结负载测量；逐 rank、逐设备核对计算与通信事件 |
| 清理 | 核对本任务进程、端口和设备资源已经释放 |

每个平台使用自己的运行证据。预检与结果必须对应当前实验和实际选中设备。设备变化后重新检查映射、健康与占用，记录新的尝试；已开始执行的实验保留原配置和结果。

## 分开查看三种结果

`execution_completed` 表示规定的执行协议已经结束。固定评测同时保留请求成功数、失败数、超时、跳过和输出截断，便于判断模型实际完成了哪些请求。

`quality_status` 表示评分是否达到预设阈值。阈值为 `null` 时仍运行固定评测并记录分数，状态为 `not_specified`。质量阈值由任务合同确定。

`business_acceptance` 汇总本次必做阶段。各项证据齐全并满足要求时为 `ACCEPTED`；其余情况为 `INCOMPLETE`，同时列出具体原因。HTTP fixture 单独标记为编排验证。

外层运行工具在模型退出后补齐清理回执时，使用独立验收入口：

```bash
fullnet verify --model <model> --run <run>
```

该命令读取原始评测、阶段产物和新的清理记录，更新验收结果，不启动服务或重新发送评测请求。只有 `ACCEPTED` 返回退出码 0；缺项和未指定的质量阈值仍列出原因。清理记录需要产生于本次停止检查之后，启动前的空卡记录保留为启动证据。

## 先验证功能，再采性能

功能优先的实验在计划中明确选择 `quality-only`，性能与 profile 记为 `deferred_by_user`。单独延后某一项时，仅延后配置中列出的阶段。后续采样使用新的实验计划，保留先前模型与评测记录。

完整实验使用冻结的性能负载和 profile 配置。profile 沿用官方导出与现有逐设备验证流程，保存正时长的设备计算事件、通信事件及原始来源。导出状态和验证结果分别记录。

## 跨机等待与恢复

跨机任务为每个角色保存 host、job、request 和尝试编号。断线后先查询这些原任务，再接续未完成阶段。等待资源时只做必要的只读查询，模型任务在两次新鲜设备检查通过后提交。

如果资源在选卡后变化，程序先区分任务是否已经入队。尚未入队的意向直接撤回；已经入队的作业需要取得完整的“模型未开始”证据，并核对本任务资源已清理，随后返回原队列。实际模型错误进入调试流程，保留首错及日志。

跨机 TP 的 rank 证据来自各角色实际所在主机的 Ray Worker 日志。收集器核对当前 case、rank、world size 和模型加载完成记录，并保留原始日志路径。两端结果汇聚后，再与本次部署合同逐项比较。

## 旧实验与源码更新

已有实验继续读取原记录，新阶段合同用于新计划。正在执行的模型保留当前源码；更新先暂存到项目发布目录，待原任务结束并完成资源核对后切换。下一次提交核对实际加载的已发布源码。
